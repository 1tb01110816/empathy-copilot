# 共情副驾 Empathy Copilot

> 欧莱雅第二届美妆科技黑客松 · 赛题一「数据共情者」参赛作品（个人参赛）
>
> 千牛客服工作台右侧辅助插件：以一个共情引擎同时服务**客服侧**（实时副驾）与**消费者侧**（温度表达 + 进度回执），把"安抚情绪"变成"可执行、可对账"的服务链路。

---

## 一、赛题要求 → 实现映射

| 赛题要求 | 本作品实现 |
| --- | --- |
| 多源跨维度融合（文本对话 × 结构化订单 × 工单） | `server/src/engine/fusion.js` 把聊天消息、订单表、5 类工单表按买家/订单号/时间窗对齐，融合为会话画像（复购、历史工单、当前订单状态、物流轨迹），驱动后续所有分析 |
| 阿里开源大模型（通义千问）为底座 | `server/src/llm/qwen.js` 接入 DashScope OpenAI 兼容端点：`qwen-plus` 做情绪复评 / 5 秒摘要 / 共情话术（流式）；`qwen-vl-max` 做多模态证据理解（破损照片 / 色差实拍 / 聊天截图）。无 Key 时全链路自动降级为本地规则引擎 |
| 探索多模态数据分析 | 聊天中的图片证据（破损泵头、空包裹、错发色号、过敏实拍、退款截图等 10 类）经 `qwen-vl-max` 输出结构化判断（结论 / 细节 / 建议追问），并回流到风险分级 |
| AI Agent 工作流 | `server/src/pipeline.js` 编排：感知(多源融合) → 并行分析(意图/情绪/风险/证据) → 决策(话术生成) → 对账(验收)；全过程经 SSE 实时推送前端，右侧面板可见每一步 trace |
| Vibe Coding 完整系统 | 前端 `web/`：三栏工作台（会话列表 / 聊天回放 / 副驾面板）+ 消费者端手机视图 + 数据洞察页，全部可点击、可操作 |

## 二、快速开始

环境要求：**Node.js ≥ 20**（推荐 22）。

```bash
cd empathy-copilot

# 1. 安装依赖（npm workspaces：server + web）
npm install

# 2. （可选但推荐）配置通义千问
#    复制 server/.env.example 为 server/.env，填入 DashScope API Key
#    Key 申请：https://bailian.console.aliyun.com/ → API-KEY 管理
#    不填 Key 也能完整运行（规则引擎模式），填入后自动切换为 Agent 模式

# 3.（可选）接入 MySQL：在 server/.env 填 DB_HOST / DB_PASSWORD 等（见「五、MySQL 接入」）
#    连接成功自动建库、导入 8 张 MOCK 表并持久化试跑记录；不配置则沿用 JSON + 内存模式

# 4. 同时启动前后端
npm run dev
#    server → http://localhost:8787（API + SSE）
#    web    → http://localhost:5173（开发页，/api 代理到 8787）
```

打开 http://localhost:5173 即进入工作台。生产构建：`npm run build && npm start`（由 server 托管 `web/dist`）。

## 三、演示脚本（评委走查路线，约 5 分钟）

### 演示线 1：S00010 面膜过敏泛红（红 · 健康风险）

1. 工作台左侧点开 **S00010**：中间回放聊天，买家上传全脸泛红照片并描述刺痒。
2. 右栏看副驾：
   - **01 多源融合**：聊天 × 订单（该单商品/金额）× 工单（历史售后）三源对齐；
   - **02 分析**：意图"不良反应/泛红刺痒"、情绪曲线峰值出现在照片消息后，**多模态证据**给出图片结构化判断（qwen-vl-max，未配 Key 时显示规则口径）；
   - **03 风险**：红色 + 原因 + 合规提示，动作建议"登记不良反应单 / 升级专员"；
   - 话术区一键 **采纳并发送**（填入回复框，可编辑）。
3. 点 **登记不良反应单** → 生成 BLFY 单号 → 切到顶部「消费者端」页：手机视图中出现进度推送"已登记…24 小时内回访"。
4. 在回复框 **采纳并发送** 副驾话术后，买家侧会自动出演下一条回应（演示模拟）：首条回复后买家"缓和等待"，继续发送跟进话术后买家"确认解决"（闭环达成，话术更新为收尾安抚）；**买家确认解决后再发送的收尾话术不再出演回复，会话就此收尾**。发送内容会同步到消费者端。
5. 想看大模型全链路：右栏点 **Agent 模式重跑**（需已配 Key），步骤条逐项亮起，话术流式打字。

### 演示线 2：S00003 保价被拒 → 50 元券（黄 · 流失风险）

1. 打开 **S00003**：刚买 3 天降价 40 元，客服答复"超 15 天价保无法补差"，买家情绪抬升。
2. 副驾识别"比价/保价"场景 + 情绪拐点，给出**发无门槛券**的挽回动作与安抚话术。
3. 点 **发放无门槛券** → HV 券号入账 → 消费者端出现"50 元无门槛券已发放，30 天有效"。
4. 回到「数据洞察」页，该会话引擎判定（黄）与数据标注（发券）一致。

### 演示线 3：S00024 空包裹（红 · 资损风险）

1. 打开 **S00024**：买家称收到空箱、要求仅退款，情绪激烈。
2. 副驾判定高风险：提示**不可直接仅退款**，动作建议 **转风控核实**（保留面单、核验称重/揽收记录）。
3. 点 **转风控核实** → KOC 单号 → 消费者端收到"核实中，请先保留外箱和面单"的进度安抚。
4. 洞察页确认：引擎 vs 标注 3 项（场景/等级/动作）全对齐。

### 演示线 4：S00018 错发色号实拍（黄 · 多模态）

1. 打开 **S00018**：买家实拍收到的口红色号，与下单色号不符。
2. 副驾 02 卡出现**多模态证据理解**：「色号错发对比」结论 + 客观发现 + 下一步建议（配 Key 后由 qwen-vl-max 输出，未配 Key 展示规则口径兜底）。
3. 动作建议补发换货、运费店铺承担 → 点 **执行** 生成 BH 单 → 消费者端同步补发进度。

### 现场试跑（评委随机出题）

1. 左栏点 **＋ 试跑新问题**：粘贴任意买家消息（一行一条模拟多轮对话），可选上传一张买家图片，并选择**买家画像**（急躁型 / 犹豫型 / 理性型）。**演示模式默认勾选**。
2. 演示模式会自动出演完整的多轮对话直到问题解决（4 条模拟消息）：**客服共情回复 → 买家缓和回应 → 客服跟进确认 → 买家安心收尾**，出演按所选**画像风格**演绎（急躁型措辞直接、犹豫型反复确认、理性型就事论事）。客服话术复用同一套场景模板（与右栏口径一致），且会**「接情绪」**：买家当前情绪较强时，话术前缀差异化（如"理解您现在的着急，马上为您跟进处理"）；有 Key 时由 qwen-plus 扮演买家生成，未配 Key 用画像模板兜底。买家反应进入情绪计算后，右栏情绪曲线持续回落（如 37.5 → 27.4 → 16.1 → 10.8，收尾状态「满意」），形成"共情有效"的完整闭环。仅追加演示对话，**不执行任何工单/发券等动作**。
3. 提交后自动打开新会话（TRY 前缀），走同一套共情引擎与 Agent 工作流：意图 / 情绪 / 风险 / 话术 / 动作建议实时输出（例：输入"面霜用后发红刺痒 + 要投诉"→ 不良反应/泛红刺痒 · RED · 停用+登记+回访动作）。模拟消息在聊天流中带 **「演示模拟」** 徽标，消费者端同步可见。
4. 人工也可以接管：在回复框采纳话术/手打内容点 **发送**，买家侧按会话画像自动出演下一条回应（首条"缓和等待"，继续发送则"确认解决"，多轮直至闭环），逐条追加到会话并参与情绪曲线计算；消费者端实时同步这段对话。**共情话术随对话轮次演进**：开场共情（未发送）→ 跟进推进（发送后买家有新反馈）→ 收尾安抚（买家确认收尾/多轮后闭环），话术卡片带阶段标签。**买家确认解决（人工发送满 2 轮）后的收尾发送不再出演回复**，弹出"已闭环收尾、买家无需继续回复"提示，演示在此优雅收尾。
5. 对账卡自动跳过（现场输入没有赛题标注）；动作执行与消费者端进度回执照常可用，形成双端闭环。
6. 试跑会话上限 20 条：默认（内存模式）重启即清空；接入 MySQL 后**持久化保存**，可在列表中点 × 单条删除、点分组头「清空」一键清空。试跑记录与赛题 138 条数据物理分离（独立表），删除只影响 TRY 前缀记录，不触碰对账口径。
7. 工作台右上角 **导出演示报告**：一键导出当前会话的完整演示链路（会话概览 / 多源融合 / 意图情绪 / 风险动作 / 完整对话 / 已执行动作），生成自包含 HTML 文件，可直接浏览器打开或打印 PDF 留存。

### 收尾：数据洞察页

- 顶部 KPI + **留出集评估**：按标注场景大类分层、用 SHA-256 确定性划出 42 条（30%）留出集，**留出集严格场景一致率 92.9%**（39/42，精确细分场景、不做等价归并）；内测集 96 条严格 95.8%，全量 138 条严格 94.9%。等价归并口径（场景大类/等级/动作覆盖）在 UI 中并列展示，不再只报单一 100%；
- 留出集清单与分层明细见 `server/data/holdout.json`，可用 `node server/scripts/build-holdout.js` 复算；严格不一致的 7 条集中在「包裹破损 / 漏发赠品」等业务等价场景；
- 风险分布环图、高频场景 TOP、情绪峰值 TOP8、工单热点；
- 底表支持「仅演示线 / 仅留出集 / 仅严格不一致」筛选，任意行点击跳回工作台对应会话。

## 四、核心设计

### 一个引擎，双端输出

```
             ┌──────────────────────── 客服侧（工作台右栏）────────────────────────┐
聊天消息 ─┐  │ 01 多源融合 → 02 意图×情绪×证据 → 03 风险×动作×话术 → 04 验收对账   │
订单表  ─┼─→│  五秒摘要 / 情绪曲线 / 合规提示 / 一键采纳发送                        │
工单表  ─┤  └──────────────────────────────────────────────────────────────────────┘
图片证据 ─┘        │
                   └── 动作执行层（登记/补发/转风控/发券/打款/退款/升级）
                          │  工单号回执 + 话术化进度文案
                          └──→ 消费者侧（进度回执 / 温度表达）
```

### 情绪曲线（规则引擎，负责"快而稳"）

- 词典命中 → 单条情绪分；会话内 EMA 平滑（α=0.65）得到曲线；
- 峰谷拐点检测；红/黄/绿三档阈值 (82/62/45) 与风险分级联动；
- 校准口径：138 个会话在等价归并口径下场景/等级/动作覆盖全一致；为校正「全量内测 = 100%」的乐观偏差，洞察页同时报告 42 条分层留出集的**严格场景一致率 92.9%** 与内测/全量对照（`server/scripts/engine-check.js --all` 可复现）。

### Agent 工作流（通义千问，负责"懂而暖"）

SSE 事件流：`step`（工作流节点：感知/意图/情绪/风险/证据/情绪复评/摘要/话术/合规过滤/对账）→ `partial`（各卡片中间结果）→ `reply_delta`（话术流式）→ `done`（最终分析）。

无 `DASHSCOPE_API_KEY` 时每一步自动降级为规则结果并在 UI 标注「规则/降级」，**不阻塞演示**。

- **合规过滤**：模型话术先完整生成并做后置扫描（医疗诊断/用药、治愈功效保证、超权限赔付、站外交易、敏感信息收集），命中即整段替换为规则安全话术，再分片安全回放——不安全内容不会先流入聊天/话术区；
- **可观测性**：每次 LLM 调用记录模型、耗时与 prompt/completion/total tokens，工作流 trace 底部汇总调用次数/token/耗时及合规过滤结果；`GET /api/llm/usage` 返回进程内累计用量。

### 业务价值代理指标（洞察页，全量 138 会话可复算）

无真实 CSAT/NPS 标签，因此不编造满意度，全部指标由会话时间戳、轮次、情绪曲线与买家画像确定性地推导，并在 UI 标注「代理口径」：

- **响应效率**：首响均值 / P90、≤60s 达标率、平均会话时长（首末消息间隔）；
- **互动深度**：买家平均发言数、图片会话占比；
- **关系与风险**：老客复访会话占比（画像历史接待 >1）、高风险会话占比（引擎红档）；
- **情绪结果**：明显情绪缓和率（峰值 ≥45 且结束较峰值回落 ≥10 分）、买家正向收尾率（末条买家消息正向词）。

## 五、MySQL 接入与试跑记录持久化（可选）

默认零配置即可完整运行（JSON + 内存，重启清空试跑记录）。如需演示真实数据库接入，在本机 MySQL 8 上启用：

```bash
# 1. 在 server/.env 填写数据库连接（未配置或连接失败会自动降级，不影响演示）
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=root
DB_PASSWORD=你的MySQL密码
DB_NAME=empathy_copilot

# 2.（可选）手动导入赛题 8 张 MOCK 表；不执行也没关系，服务启动时检测缺表会自动导入
npm run db:import -w server
```

接入后：

| 能力 | 说明 |
| --- | --- |
| 赛题数据入库 | 8 张 MOCK 表（chat / orders / 5×tickets / datadict）以同构表导入 `empathy_copilot` 库：列名与 JSON 表头一致（中文原名），全 TEXT + utf8mb4，引擎逻辑零改动 |
| 试跑记录持久化 | `try_sessions` / `try_messages`（外键级联）持久化试跑会话与消息；试跑会话中执行的动作与消费者端推送存入 `runtime_actions` / `runtime_messages`——服务重启后仍可回看 |
| 在线删除 | 会话列表试跑分组：每条右侧 **×** 单条删除；分组头 **清空** 一键清空（带确认）。删除同步内存 + MySQL，仅作用于 TRY 前缀记录 |
| 自动降级 | 未配 `DB_HOST` 或连接失败/读取异常时，console 提示原因并完整回退 JSON + 内存模式；`/api/overview.storage` 与前端的「存储」角标会显示当前模式 |
| 口径隔离 | 138 条赛题会话与其洞察对账始终只读内存快照，试跑表物理分离；试跑/删除操作不会污染一致率口径 |

## 七、主要 API

| 接口 | 说明 |
| --- | --- |
| `GET /api/overview` | 数据集统计 + LLM 状态 + 存储模式（memory/mysql）+ 演示线 + 一致率概览 |
| `GET /api/sessions` | 会话列表（含引擎判定风险等级/峰值） |
| `GET /api/sessions/:id` | 会话详情：消息 + 订单 + 工单 + 规则剖析 + 已执行动作 |
| `GET /api/sessions/:id/stream?upto=&mode=` | **SSE** Agent 工作流事件流（mode 取 `agent` / `rules`） |
| `POST /api/sessions/:id/action` | 执行动作（登记/补发/转风控/发券/打款/退款/升级） |
| `POST /api/sessions/:id/send` | 人工发送回复 → 买家侧自动出演下一条回应（首轮缓和、之后确认解决）；买家确认解决后的收尾发送不再出演（返回 `ended:true`，只追加客服消息）。试跑会话进消息流、真实会话进演示隔离层，均不执行动作 |
| `POST /api/sessions/:id/reset` | 一键重置演示状态：清空真实演示会话的运行时动作 / 消费者回执 / 人工发送对话层；不触碰赛题 138 条数据（试跑会话请删除重建） |
| `POST /api/try` | 现场试跑：创建试跑会话（文本+可选图片 dataURL+可选关联订单/工单 orderId/ticketId+可选买家画像 buyerType），走同一引擎/Agent 工作流，不参与对账统计；`demo: true` 自动出演多轮对话直至解决（按画像风格出演，只演不做）；接入 MySQL 时自动持久化 |
| `GET /api/refs/orders?q=` | 试跑可选关联：从赛题 MOCK 库搜索订单（订单号/商品名/买家/物流单号等关键词） |
| `GET /api/refs/tickets?q=` | 试跑可选关联：从赛题 MOCK 库搜索工单（工单号/订单号/症状/原因等关键词） |
| `DELETE /api/try/:id` | 删除单条试跑记录（内存 + MySQL 同步，含其运行时动作/推送；仅 TRY 前缀，不触碰赛题数据） |
| `DELETE /api/try` | 清空全部试跑记录 |
| `GET /api/insights` | 全量 138 会话聚合 + 留出集/内测集/全量一致率 + 严格不一致清单 |
| `GET /api/llm/usage` | 进程内 LLM 调用累计：次数/失败数/token/耗时，按 kind 与模型分组 |

入参校验：会话 ID 仅允许字母/数字/下划线/中划线（≤32 字符）；动作类型必须在 7 类白名单内，payload 仅接受 ≤2KB 普通对象且校验金额/加急字段；SSE `upto` 必须为 1–1000000 的整数；试跑文本 ≤2000 字、图片仅接受 png/jpeg/webp/gif 且 ≤3MB、买家画像必须为已知枚举。非法入参在业务逻辑前返回 400。

## 九、公网部署（Railway）

- 演示链接：https://empathy-copilot-production.up.railway.app
- GitHub 仓库：https://github.com/1tb01110816/empathy-copilot（public）
- 部署方式：Railway 免费 Trial 连接 GitHub 仓库，**main 分支开启自动部署（push 即触发）**；Railpack 自动构建 `npm install; npm run build`，启动命令 `npm run start`，监听端口由平台自动注入
- 本地推送 `git push origin main` 后无需任何平台操作，约 1-3 分钟自动构建上线
- **访问口令（建议开启）**：在 Railway Variables 设置 `APP_ACCESS_CODE`（用户名默认 `demo`，可用 `APP_AUTH_USER` 覆盖）。设置后全站启用 Basic Auth，浏览器首次访问会弹出口令框；`/api/health` 保持免鉴权，供平台/监控探活。留空则不启用，本地开发不受影响。
- **限流与体积上限**：全 API 每 IP 240 次/分钟，写接口 60 次/分钟，Agent 流式分析 20 次/分钟，试跑创建 10 次/分钟；JSON 请求体上限 4MB，试跑图片上限 3MB。超限返回 429/413（JSON 错误体），不会影响正常演示操作。
- **线上存储口径**：当前 Railway 实例为**内存模式**——试跑记录仅保存在进程内存，平台重启 / 重新部署即清空；赛题 138 条 MOCK 数据为只读快照，不受影响。需要持久化时按第五节配置 `DB_HOST` 等变量，重启后自动切到 MySQL。工作台顶栏与页面横幅会显式标注该状态。
